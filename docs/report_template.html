The finding

Almost nothing that went wrong was a science problem

Nine tools ran against one predicted DIO3-cut structure (mean pLDDT 86.3), 40 designs each, one job per tool so per-design cost stayed visible. Seven completed on the first or second attempt. The two that did not were stopped by a CUDA architecture mismatch and a missing Python package — neither of which any amount of protein-design expertise would have predicted.

The expensive category is worse than a crash: six of the bugs found do not raise at all. They produce a full, well-formed output file that is wrong. A harness that only checks exit codes catches none of them.

Utilisation

Low GPU utilisation is normal here — except when it isn't

A measurement trap worth encoding. jobstats reported “GPU utilization 0% <-- GPU was not used” for a job whose GPU memory it simultaneously reported at 76 GB. Its sampler is too coarse for short jobs. The 15-second nvidia-smi trace these figures are built from exists because of that.

Batching

What a bigger batch actually buys, measured

Three tools expose a batch knob, so we swept them. The result is not one answer — it is three different ones, which is itself the point.

ToolChangeWall clockPeak GPUVerdict
Caliby batch 4 → 16, 8 seqs 2.9 → 2.3 min 4.1 → 14.5 GiB 6× throughput at the best point (1,280 sequences in 7.2 min)
BoltzGen batch 1 → 40 22.9 → 15.0 min 7.3 → 7.1 GiB 34% faster at flat memory — memory is not its constraint at all
Proteina-Complexa batch 8 → 16 25.9 → 23.5 min 15.9 → 24.6 GiB 9% for 55% more memory — not worth it; its idle time is AF2
Throughput and utilisation are different objectives. BoltzGen got 34% faster while its utilisation moved only 56% → 61%, because the win was 40 trunk runs collapsing to 1 — not a fuller GPU. Proteina-Complexa's utilisation rose and bought almost nothing. Utilisation is a diagnostic; designs per GPU-hour is the goal.

Silent failures

The bugs that cost a campaign rather than an hour

None of these raise an error. Each produces output that looks entirely normal. They are the reason the harness needs preflight assertions rather than post-hoc checks.

Exit status is not a success signal either. Genie 3's fixed run logged “Run completed”, wrote 40 sequences, 40 backbones and 200 AF2 outputs — and sacct recorded FAILED. The cause was a trailing find … | head in our own launcher: under set -o pipefail the SIGPIPE fails the pipeline, and a job's exit status is its last command's. Trusting sacct would have discarded an hour of correct work.

The specification

Nine things the library has to absorb

Each of these is here because something above proved it was needed. Ordered by how much of the design it constrains.

01

A Target is not one thing, and the harness must own the conversion

The brief supplied a sequence and an MSA. The tools wanted, between them: sequence only; PDB; mmCIF; a structure plus a two-file MSA directory; a problem-set directory of JSON and per-chain trees; and an entry appended to a Hydra registry that lives read-only inside an image. Two of those cannot be produced by format conversion at all.

Fold once, cache every representation. It is also the only way a cross-tool comparison means anything — otherwise each tool folds the target with whatever it ships.

02

“Generate N designs” is not portable — model three numbers

Every tool interprets a count differently: generated, accepted, post-filter, or padded with failures to hit N. The schema needs attempted / produced / passed as separate fields plus the filter that produced the third.

A single n_designs field records “40” for both PXDesign and Genie 3, hiding that one had 5 dual-filter passes and the other had none.

03

Output adapters are unavoidable

Only one tool writes a FASTA. Elsewhere sequences live in a CSV column and no two name it the same. One column that looks like a sequence is actually integer indices — its real sequence has to be read off a PDB chain. Chain conventions are inconsistent: RFdiffusion makes the binder chain A, Proteina-Complexa makes the target chain A.

Write adapters against observed output, not upstream docs — several document output paths and flags the code does not have.

04

Environment hygiene belongs in one place

Three tools broke on two host-environment problems with nothing to do with protein design: TMPDIR on Lustre kills any Triton-JIT tool, and the host's RHEL CA bundle breaks httpx inside every Ubuntu image at import.

It should be impossible for a tool driver to opt out of the launch layer.

05

Preflight assertions are the highest-value code in the harness

Check the resolved checkpoint against the requested mode; check the constraint file covers every input; check the framework resolved to a GPU backend; echo the resolved config and diff it against the requested one. Refuse to launch, don't warn.

Every silent failure in the table above is cheap to assert before the GPU work starts.

06

Success is “the expected artifacts exist and parse”

Exit status is corroboration only. The adapter already knows what the artifacts are, so it should own the predicate.

07

Probe image capability; don't read the manifest

A weight audit that asks only “are the checkpoints present” passes both of the worst images here. One has all nine checkpoints embedded and cannot execute a single CUDA kernel on H100. The other has every weight and shipped a CPU-only JAX. Both were documented as fine.

Generate capability metadata by running a probe on the target GPU class, and store it beside the SIF checksum — along with any overlay, since the image alone then no longer determines the result.

08

Measure resources, then reuse them

Collect sacct plus a sampled nvidia-smi trace on every run and derive the next request from history. Label every GPU-memory figure with the allocator convention behind it.

09

Know the scheduler's realities

Cluster reservations silently defer long jobs — a walltime that overlaps a maintenance window does not queue, it waits until after. Resume-safety varies per tool and should be declared: one skips work already done, one silently no-ops a rerun, and one has no seed at all, so its runs are not reproducible and cannot be split across jobs.

Scope

What this run deliberately does not tell you

There is no cross-tool quality comparison here, and the numbers in the full report should not be read as one. Every score comes from a different scorer, mostly the same model that produced the design, evaluating its own work. Running all designs through one common scorer is the next step.

The one comparison that is fair is amino-acid composition, measured identically for everything. Every tool sits well below natural protein (Shannon entropy 3.15–3.72 against ~4.1), which is expected for de novo binders — but the spread is large, and the alanine-rich end is the classic gradient-hallucination failure mode. Inverse folding onto a fixed backbone produced the cleanest composition of anything tested.

The epitope question is also open. Eight tools ran without hotspots and each chose its own surface, so they are unlikely to agree. The one tool given hotspots achieved a median coverage of zero — the conditioning did not take, which is a finding about conditioning strategy rather than sample size, and worth chasing before that tool is scaled up.

Two images need rebuilding before their tools are first-class: one for sm_90 support, one for a GPU-capable JAX. Both are one-line dependency changes and each currently costs a whole tool.
